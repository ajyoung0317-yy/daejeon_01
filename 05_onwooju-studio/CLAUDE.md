# 온우주 스튜디오

온우주(onspace)는 AI 에이전트가 조사와 제작을 맡고 운영자(애매필)가 감상과 관점을 더하는 영화 콘텐츠 스튜디오다. 극장 개봉작과 OTT를 가리지 않는다.
이 폴더가 **본사**다 (2026-11-11 블로그 폴더를 합침). 회사 문서, 블로그 결과물, 쇼츠, 에이전트가 모두 여기 있다. 예전 `클로드/netflix-blog/netflix-blog-automation`은 보관용이라 쓰지 않는다.

## 회사 문서 (모든 작업의 기준)
| 문서 | 내용 |
|---|---|
| `회사/운영계획서.md` | 목표, 채널 역할, 로드맵, 지표 |
| `회사/브랜드-가이드.md` | 이름 표기, 말투, 색, 고정 요소. **가이드끼리 다르면 이 문서가 우선** |
| `회사/원소스-멀티유즈.md` | 작품 하나를 블로그·카드뉴스·쇼츠로 쓰는 흐름 |
| `회사/작품장부.md` | 작품마다 어느 채널까지 끝났는지. **채널 하나가 끝날 때마다 갱신** |
| `회사/learnings.md` | 배움 기록. 작업 설계 전에 먼저 읽고, 끝나면 한 줄 추가 |
| `회사/성과/` | 채널 숫자 기록(`채널-월별.csv`, `콘텐츠별.csv`)과 월간 리포트. 사용자가 숫자를 알려 주면 **메인이 CSV에 한 줄씩 넣는다**(성과팀은 읽기만). 매달 초 `performance-analyst`가 지난달 리포트를 쓰고, 그 제안을 `content-planner`가 다음 달 캘린더에 반영한다 |
| `회사/캘린더/YYYY-MM.md` | 월간 발행 캘린더. 매달 말 `content-planner`(기획팀)가 다음 달 것을 만든다. "이번 주 할 일"을 물으면 이 파일을 본다. 같은 달 파일이 여러 개면 **가장 높은 `_vN`이 최신** |

## 새로 볼 작품 / 본 작품 → `weekend-review` 스킬
운영자의 기본 루틴은 **주말에 새 작품을 보고 블로그·카드뉴스·릴스를 내는 것**이다. "○○ 준비해 줘", "○○ 봤어"처럼 새 작품 이야기가 나오면 `.claude/skills/weekend-review/SKILL.md`를 따른다 (관람 전 준비 → 감상 받기 → 세 채널 동시 초안 → 검수 → 운영자 확인 2번 → 마무리). 감상 양식은 `회사/감상-양식.md`.

## 작품 이름을 받았을 때 (원 소스 멀티 유즈)
1. `회사/작품장부.md`에서 그 작품 줄을 찾아 무엇이 있고 없는지 사용자에게 알린다.
2. **조사**: `output/[주제]/research.md`가 없으면 먼저 만든다. 있으면 재사용한다.
3. **감상**: `영화인스타그램/영화/[작품]/감상.md`가 없으면 사용자에게 **한 번만** 감상·별점을 받아 만든다. 운영자 감상·별점은 모든 채널이 이 파일에서만 가져온다.
4. **채널**: 사용자가 고른 채널만 돌린다. 블로그 = `movie-blog-review` 스킬, 카드뉴스 = `card-news` 스킬, 쇼츠 = 아래 영상팀.
5. 끝나면 작품장부 갱신, learnings 한 줄.

- **같은 작품 찾기**: 이름에서 띄어쓰기·`-`·`_`, 앞 번호(`08_`), 뒤 `_리뷰`를 빼고 비교한다. `output/`에 같은 작품 폴더가 이미 있으면 새로 만들지 않고 그 폴더를 쓴다.
- **바깥 폴더**: 스틸 보관함과 감상은 `C:/Users/jinsu/OneDrive/바탕 화면/클로드/영화인스타그램/영화/[작품]/`, 카드뉴스는 `…/영화인스타그램/posts/`.

## 토큰 아끼기 (2026-11-12)
에이전트 한 번 호출에 3만~8만 토큰이 든다 (지침·회사 문서·조사 자료를 매번 새로 읽기 때문). 하트 오브 비스트 쇼츠 1편에 약 60만 토큰이 들었다.
- **검수는 묶는다**: 한 작품에 `brand-reviewer`는 초안 1번(세 채널 함께) + 최종 1번.
- **장면 검토는 디렉터가 직접**: 장면 PNG를 한 장으로 모아 보고, 문제 장면만 돌려보낸다.
- **지시문에 읽을 범위를 적는다**: "영상팀-구상 3·5장만", "research.md 핵심 정리와 출처 목록만"처럼. 문서 전체를 읽히지 않는다.
- **이어 고치기는 3번까지**: 같은 에이전트를 SendMessage로 3번 넘게 고치면 쌓인 대화가 비싸진다(캘린더 v5 때 한 번에 약 26만). 그 뒤에는 요약을 주고 새로 부른다.
- **결정은 처음에 모은다**: 관람 요일, 대상 작품 범위, 지난 작품을 쓰는지, 협찬 여부를 작업 시작 때 한 번에 묻는다.
- **가벼운 모델**: `shorts-editor`, `performance-analyst`는 Sonnet으로 돈다(에이전트 파일 `model:`). 판단이 중요한 기획·검수·글은 기본 모델.

## 메인의 역할: 오케스트레이터
- **메인은 직접 리서치하거나 글을 쓰지 않는다.** 모든 작업은 서브 에이전트나 스킬에 맡긴다.
- 메인이 하는 일: 단계 호출, 산출물이 생겼는지 확인, 검수 결과 저장, 사용자에게 진행 상황 알리기.
- 서브 에이전트 타입이 목록에 없으면 general-purpose 에이전트에게 "`.claude/agents/[이름].md`를 읽고 그대로 따르라"고 지시한다.
- **단계가 끝날 때마다** 사용자에게 1~2줄로 알린다: 무엇이 끝났고, 핵심 결과, 다음 단계.
- 에이전트가 문제(확인 필요 정보, 검수 실패)를 보고하면 그대로 사용자에게 전하고, 고칠지 묻는다.

## 스킬 (사용자 설정 폴더 `~/.claude/skills/`에 있음)
- 블로그·카드뉴스 규칙의 원본은 스킬이다. 스킬을 고쳤으면 커밋 전에 `py tools/backup_skills.py`로 `회사/스킬-백업/`을 갱신한다.

## 블로그 글을 쓸 때
1. **`movie-blog-review` 스킬**로 조사 → 원고 → 썸네일 → `final.md`/`final.html`까지 만든다. 작품 폴더에 `감상.md`가 있으면 스킬이 ✍️ 자리와 온우주별점을 거기서 채운다.
2. **검수**: `brand-reviewer`를 새로 불러 `final.md`를 검토받는다. 판정은 메인이 `output/[주제]/reviews/blog.md`에 저장한다. "수정 후 통과"나 "재작업"이면 사용자에게 전하고 고칠지 묻는다.
3. 작품장부 블로그 칸 갱신, 마지막에 사용자가 직접 할 일(✍️ 남은 자리, 공식 스틸, 공식 페이지 재확인, 발행)을 정리해 알린다.

## 쇼츠·릴스를 만들 때 (영상팀)
설계 근거는 `회사/영상팀-구상.md`. 자막만 쓰는 1080×1920 세로 영상. 결과물은 `output/[주제]/shorts/`.

| 단계 | 누가 | 산출물 |
|---|---|---|
| 1. 접수 | 메인 | `shorts/brief.md` (작품, 영상 종류, **운영자 감상 3줄·별점**). research.md가 없으면 `researcher` 먼저 |
| 2. 기획 | `shorts-planner` → 검토 `brand-reviewer` | `shorts/01_plan/plan.md`, `shorts/reviews/01_plan.md` |
| 3. 운영자 확인 | 사용자 | 훅·자막 선택과 수정 → `shorts/decisions.md` |
| 4. 화면 | `shorts-designer` → **디렉터가 직접 검토** (장면 모음 한 장. 구성을 바꿔야 할 때만 `shorts-planner`) | `shorts/02_frames/scene-NN.png`, `shorts/reviews/02_frames.md` |
| 5. 편집 | `shorts-editor` → 최종 검수 `brand-reviewer` | `shorts/03_edit/[주제]_v1.mp4`, `shorts/reviews/03_final.md` |
| 6. 보고 | 메인 | `shorts/final-report.md`, `회사/learnings.md`에 한 줄 |

- 운영자 감상·별점은 지어내지 않는다. 없으면 접수 단계에서 사용자에게 받는다.
- 검토는 만든 에이전트가 아닌 **정해진 검토자를 새로 호출**한다. `brand-reviewer`는 파일을 쓰지 않으므로 판정을 메인이 `reviews/`에 저장한다.
- 지시문에는 6요소를 넣는다: 프로젝트 폴더 · 먼저 읽을 파일 · 할 일 · 산출물 경로 · 완료 기준 · 쓰기 허용 폴더.
- 결과가 충돌하면 메인이 근거를 비교해 정하고 `decisions.md`에 이유를 남긴다. 큰 방향 전환은 사용자에게 묻는다.
- 업로드는 사용자가 직접 한다. 음악도 업로드할 때 사용자가 넣는다.
